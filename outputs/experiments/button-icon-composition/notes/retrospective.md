# Ретроспектива

Закрытие эксперимента `button-icon-composition`. Ветка
`experiment/button-icon-composition`. Этот файл — итоговый вывод по работе;
детали и оценки остаются в `notes/results.md` и `notes/comparison.md`.

## Цели

1. Связать `Button` и `Icon`: сделать `Button` ответственным за создание и
   оформление вложенных иконок.
2. Проверить, достаточно ли публичного контракта `Icon` для такой композиции.
3. Оценить, даёт ли разделение на публичный `Button` и приватный node-based
   `_Button` доказуемую пользу.
4. Сохранить поведение нативного `<button>` и подтвердить результат в коде и
   браузере.

## Достигнуто

- Публичный `Button` принимает `prefixIcon?: IconName` / `suffixIcon?: IconName`
  и сам создаёт `Icon`; потребитель больше не создаёт `Icon` вручную.
- Соответствие `ButtonSize → IconSize` принадлежит `Button` и не выводится из
  совпадения названий.
- Цвет разделён по семантическим ролям: `label` читает роль `text`, слоты
  `prefixIcon` / `suffixIcon` — роль `icon`; общий foreground на `root` убран.
- Контракта `Icon` оказалось достаточно: расширять его публичный API для этой
  композиции не потребовалось.
- `ref` типизирован через `ComponentProps<"button">` и проверен в браузере:
  указывает на нативный `BUTTON`.
- Иконки декоративные, доступное имя принадлежит кнопке.
- Потребители (`App.tsx`, stories) мигрированы; добавлены контрактные и
  браузерные проверки, включая проверку независимости цветовых ролей.
- Модуль экспортирует `Button` как единственное runtime-значение; публичные
  типы (`ButtonTone`, `ButtonSize`, `ButtonProps`) также доступны потребителю.

## Отменено по результатам эксперимента

- **Приватный `_Button` и `InternalButtonProps`.** Разделение входило в
  согласованную модель и было реализовано; по итогам оценки у него не нашлось
  доказуемой текущей пользы, и реализация сведена к одному компоненту. Это
  корректное исполнение дизайна эксперимента: агент проверил гипотезу,
  зафиксировал вывод с рекомендацией свернуть слой и изменил реализацию после
  решения пользователя. Публичный API, DOM и визуальный результат при
  свёртывании не изменились.
- **`tone="icon"`.** Под именем цветовой оси лежали форма и тип содержимого.
  Удалён; проектирование кнопки только с иконкой относится к отдельному
  эксперименту, а не к недостигнутым целям этого.
- **Общий foreground через `root`.** Заменён назначением цвета по слотам.
- **Прежний мягкий цвет `ghost`.** Он выражался ролью `background`, применённой
  как ink, и в матрице `text`/`icon` ролевого эквивалента не имеет. По
  согласованию выбран более контрастный цвет; изменение визуально проверено.

## Ограничения доказательств

- Проверена конкретная связка `Button → Icon`, а не универсальная система
  композиции компонентов.
- Цветовые роли подтверждены разными значениями `text` и `icon` в обеих темах,
  но динамическая смена только `icon` и цветовые роли во всех интерактивных
  состояниях отдельным сценарием не покрыты.
- Visual-проверка подтверждает внешний вид конкретных сценариев, а не
  неизменность DOM или всего поведения.
- Метрики сравнения B/C в `notes/comparison.md` исторические и не описывают
  текущий файл точно.
- Достаточность соответствия `sm → sm`, `md → sm` на будущих макетах не
  проверена.
- Отдельный компонент кнопки только с иконкой не реализован — это другая задача.

## Архитектурные выводы

1. Композиция не требует дополнительного компонента-адаптера: один `Button`
   может владеть разметкой, recipe и созданием `Icon`, оставаясь небольшим.
   Дополнительный слой оправдан только конкретной ответственностью или
   потребителем.
2. Связь независимых компонентов принадлежит месту композиции. `Icon` владеет
   своим размером, `Button` — своим; соответствие задаёт `Button`. Совпадение
   имён размеров не является контрактом совместимости.
3. Семантическая роль важнее совпадения значения. `text` и `icon` могут давать
   одинаковый цвет, но должны оставаться независимо управляемыми; слоты дают
   естественное место для этих назначений.
4. Оси вариантов должны иметь однозначный смысл. `tone` отвечает за оформление,
   а не за превращение текстовой кнопки в icon-only.
5. Отрицательный результат — полноценный результат эксперимента: проверка
   `_Button` привела к обоснованному упрощению.

## Выводы по процессу

Что сработало:

- Небольшой реальный потребитель позволил проверить API `Icon` без создания
  универсальной системы заранее.
- Ревью выявило существенные проблемы: отсутствующую типизацию `ref`,
  избыточную прослойку, смешение осей вариантов и неверную привязку цветовых
  ролей.
- Визуальные изменения согласовывались и проверялись по diff.
- Разные тестовые значения `text` и `icon` сделали семантическую ошибку
  наблюдаемой; обычный скриншот её бы не выявил.
- Порядок «предложить вывод, менять согласованную реализацию по решению
  пользователя» соблюдался.

Что улучшить:

- Сначала сверять реализацию со всей семантической моделью: первоначальная
  рекомендация оставить общий цвет на `root` не учитывала существующую роль
  `icon`.
- Проверять заявленные критерии напрямую: `ref` присутствовал в требованиях, но
  не был полноценно типизирован и проверен до отдельного ревью.
- Сокращать дублирование состояния между документами: часть заметок хранила
  исторические метрики и ссылки на удалённые артефакты.
- Отделять фактически проверенное от более широких выводов.

## Вывод пользователя о модели разработки

Модель разработки через небольшие очерченные эксперименты последовательно
подтверждает состоятельность. Через несколько экспериментов из результатов
можно будет сформировать минимальный, подтверждённый практикой каркас
разработки компонентов:

- визуальные и визуально-поведенческие компоненты;
- asset-based компоненты;
- правила написания стилей и recipes для PandaCSS;
- композиция компонентов — пока на простых, проверенных связках.

Это хорошая база для создания полноценных статических страниц.

Параллельно формируется проектный слой утилит: для шрифтов уже есть полноценные
инструменты, поэтому повторяемые операции перестают требовать ручного контроля
агента и переносятся на контракт инструмента и результат его выполнения.

Небольшие очерченные эксперименты хорошо подходят для работы с агентами; главное
— удерживаться в рамках эксперимента. Перспективное направление — проектный набор
skills по образцу superpowers, в который можно вшить предохранитель от
расползания эксперимента в контекст: агент может обнаружить смежную проблему,
исследовать её в объёме, нужном для текущей цели, и предложить дальнейшую
работу, но включение этой работы в эксперимент требует явного решения
пользователя.

Каркас разработки и skills должны расти из результатов экспериментов, а не из
предположений о будущих потребностях. На текущий момент каркас и набор skills —
направление дальнейшей работы, а не реализованный результат.
