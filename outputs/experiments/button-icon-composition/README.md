# Эксперимент: Button Icon Composition

**Статус:** active (открыт 2026-09-25). Реализация выполнена; закрытие — по
прямой команде пользователя.

Ветка: `experiment/button-icon-composition` от `main` (эксперимент
`icon-asset-component` слит в `main`).

## Вопрос

Как связать `Button` и `Icon` так, чтобы потребитель задавал иконку по имени, а
`Button` сам управлял её размером и цветом; и даёт ли разделение на внутренний
`_Button` (принимает узлы) и публичный `Button` (принимает имена иконок)
достаточно пользы, чтобы оправдать дополнительный слой.

Дополнительно проверяется, хватает ли публичного контракта `Icon` для подобных
связок.

## Scope

В рамках:

- публичная композиция `Button → Icon` по имени иконки;
- локальное в модуле `Button` соответствие `ButtonSize → IconSize`, не
  опирающееся на совпадение названий;
- цвет иконки определяется `Button` и наследуется через `currentColor`;
- оценка достаточности публичных экспортов `Icon` (`IconName`, `IconSize`,
  `className`, наследование цвета);
- сохранение поведения нативного `<button>`: атрибуты, события, `ref`,
  `disabled`, accessibility, отсутствие лишних DOM-элементов;
- сравнение с однокомпонентным вариантом на одинаковых сценариях;
- миграция текущих потребителей и stories на имена иконок.

Вне рамок:

- глобальная шкала «совместимых» размеров для всех компонентов;
- универсальная система композиции или реестр связей компонентов;
- иконки из внешних паков, `Logo`, изменения font pipeline;
- новые варианты оформления `Button`, не нужные для проверки гипотезы;
- отдельный компонент для кнопки только с иконкой (появится позднее);
- закрытие эксперимента (только по прямой команде).

## Модель (принятые решения)

- Публичный `Button` — единственный компонент модуля: он принимает
  `prefixIcon?: IconName` / `suffixIcon?: IconName`, сам создаёт `Icon` и
  владеет DOM, слотами и recipe.
- Разделение на приватный node-based `_Button` и публичный `Button`
  рассматривалось и **отменено** по ревью: слой не давал доказуемой пользы
  (`notes/comparison.md`).
- Публичные имена props сохраняются (`prefixIcon` / `suffixIcon`), меняется
  только их тип. Это осознанное breaking change: существующие вызовы с узлами
  (`<Icon />` или что-либо ещё) мигрируются.
- Размеры: `Icon` владеет своим размером и геометрией; `Button` владеет своим
  размером и геометрией слотов; явное соответствие `ButtonSize → IconSize`
  живёт в модуле `Button`. Совпадение названий (`sm` / `md`) ничего не
  гарантирует.
- Начальное соответствие: `Button sm → Icon sm`, `Button md → Icon sm` (оба
  слота сейчас `x8`). Внешний вид искусственно не меняется.
- Выравнивать нужно и glyph (`font-size`), и контейнер (ширина/высота):
  уменьшить только контейнер недостаточно.
- Цвет: `Button` задаёт оформление, `Icon` наследует через `currentColor`,
  включая состояния кнопки; отдельного `tone` у `Icon` не появляется.
- Accessibility: иконки внутри кнопки декоративные; доступное имя задаётся
  текстом или `aria-label` кнопки; вложенные иконки его не дублируют.
- Разделение не добавляет DOM-обёртку и не дублирует стили.
- `tone` — только цветовая ось (`primary | secondary | ghost`). Вариант
  `tone="icon"` удалён: под именем цветовой оси лежала форма и тип содержимого, а
  кнопка только с иконкой станет отдельным компонентом.

## Существующее состояние (исходная точка)

- `Button` принимает `prefixIcon` / `suffixIcon` как `ReactNode`.
- `ButtonSize` — `"sm" | "md"`; `IconSize` — `"sm" | "md" | "lg"`.
- `IconName` уже экспортируется публично из `src/shared/components/icon/index.ts`,
  поэтому отдельная map имён не требуется только для типизации.
- Слоты иконок `Button` имеют размер `x8` в обоих размерах кнопки.

## Сравниваемые подходы

- **A. Текущий `Button` с `ReactNode`** — исходная точка, не переписывается.
- **B. Один `Button`, который принимает имена и сам создаёт `Icon`** — итоговый
  выбор.
- **C. Внутренний node-based `_Button` + публичный icon-based `Button`** —
  основной кандидат; реализован, признан избыточным и удалён.

Для каждого фиксируем: простоту публичного API, объём кода потребителя,
количество типов и передачи props, дублирование, простоту изменений.

## Критерии успеха

- Публичный API принимает только `IconName`; неизвестное имя и передача
  `ReactNode` отклоняются типами.
- Модуль экспортирует только `Button`; внутренняя таблица размеров не
  экспортируется.
- Потребитель не выбирает размер и цвет иконки вручную.
- Соответствие размеров явно принадлежит `Button` и не зависит от совпадения
  названий.
- Prefix, suffix, обе иконки и отсутствие иконок работают в нужных размерах,
  темах и состояниях.
- Поведение нативного `<button>` сохранено: атрибуты, события, `disabled`,
  `ref`.
- Доступное имя кнопки не дублируется вложенными иконками.
- Разделение не добавляет DOM-элементов и не меняет внешний вид существующих
  сценариев.
- Сравнение с однокомпонентным вариантом зафиксировано; разделение проверено,
  признано избыточным и свёрнуто (`notes/comparison.md`).
- Выводы зафиксированы; закрытие — по прямой команде.

## Состояние (2026-09-25)

- Реализована композиция `Button → Icon` по имени одним компонентом: приватный
  `_Button` рассматривался, измерен и удалён (`notes/comparison.md`).
- `tone="icon"` удалён из `Button`: `tone` — только цветовая ось. Потребители
  (`App`, stories) обновлены, `staticCss` и recipe без `icon`, visual baseline
  пересмотрен осознанно (убрана квадратная icon-only кнопка).
- Кнопка только с иконкой — отдельный компонент, вне рамок этого эксперимента.
- Проверки: 73 unit, 14 browser, `check:deps`, `build`, `storybook:build`,
  `test:visual` — зелёные.
