# Эксперимент: Icon Asset Component

**Статус:** completed (2026-09-25).

Основной результат и source of truth — код модуля `Icon` и его инструменты.
Пользователь подтвердил работоспособность, добавив 17 иконок из design-system
панели через другую сессию агента.

## Вопрос

Как устроить компонент из принципиально другого класса — asset-компонент, чей
источник данных не визуальный дизайн и бизнес-правила, а внешний ассет (здесь —
набор SVG-иконок), и при этом получить воспроизводимый pipeline, стабильный
публичный API и безопасное обновление набора без скрытых breaking changes.

Дополнительно проверяется технология: подходит ли **icon font** как основной
runtime-формат для монохромного набора, или его следует заменить.

## Классификация

`Icon` — **asset-компонент**: класс по источнику данных и pipeline, а не по
расположению в файловой системе. Компонент лежит наравне с остальными —
`src/shared/components/icon/`.

## Scope

В рамках:

- собственный versioned набор SVG-иконок как единственный источник первой
  версии;
- процесс подготовки и валидации исходных SVG (нормализация → строгий контракт);
- pipeline `SVG → WOFF2 + manifest`, детерминированный по выходу;
- manifest со стабильными ключами и codepoint, сгенерированный TypeScript union;
- компонент `Icon`: анатомия, API, размеры, цвет через `currentColor`,
  accessibility;
- подключение ассета в проект (font-face, Storybook, использование в App);
- два project-local навыка: `build-icon-font` и `update-icon-set`;
- проверки: unit, browser/Storybook, visual, а также проверки обновления набора;
- оценка пригодности icon font против inline SVG.

Вне рамок:

- внешние икон-библиотеки;
- многоцветные/градиентные иконки, анимации;
- manifest с независимыми от имён файлов публичными ключами (будущее расширение с
  отдельной миграцией);
- интеграция с PEN;
- изменение `raw/` (immutable).

## Модель (принятые решения)

- Публичный ключ первой версии = имя SVG-файла в `kebab-case`
  (`arrow-right.svg` → `name="arrow-left"`-style ключ).
- Codepoint не зависит от порядка файлов: существующие ключи сохраняют свои
  значения, новые получают следующий codepoint после наибольшего уже
  назначенного (сортировка — только внутри пачки новых). Codepoint удалённого
  ключа может быть переиспользован: шрифт и manifest пересобираются вместе.
- `Icon` — единственный React-доступ к шрифту; публичный API: `name`, `size`,
  `label`, стандартные span-атрибуты.
- Цвет наследуется через `currentColor`; отдельного `tone` нет.
- Accessibility: без `label` — декоративная (`aria-hidden`); с `label` —
  смысловая (`role="img"` + доступное имя).
- Анатомия — один root без внутренних slots; визуальная проекция остаётся в
  компоненте, font-face — техническая регистрация ассета.
- При обновлении набора: добавление безопасно автоматизируется; изменение glyph,
  удаление/переименование ключа и коллизия имён требуют явного решения
  пользователя. Автомиграция — только статических `<Icon name="…">`.

## Критерии успеха

- Исходные SVG нормализуются и проходят строгую валидацию с понятной
  диагностикой; нарушения не «залечиваются» молча.
- Сборка детерминирована: повторный прогон без изменений не меняет шрифт и
  manifest.
- Manifest удерживает ключи и codepoint стабильными.
- `Icon` реализует принятый API и accessibility-контракт; тесты это проверяют.
- Storybook показывает набор, размеры, light/dark и decorative/labelled варианты.
- Visual-тест фиксирует реальный рендер шрифта.
- Проверки обновления покрывают addition, glyph change, rename, removal и
  коллизию имён.
- Есть обоснованное решение по технологии (icon font принят или отвергнут) на
  основе критериев, а не по умолчанию.
- Выводы зафиксированы; эксперимент завершён 2026-09-25.

## Итог

Идея подтверждена: asset-компонент выражается как тонкий runtime-адаптер при
отдельном детерминированном pipeline подготовки ассета, а публичный API и
исходные SVG не зависят от способа доставки.

Что дало результат:

- контракт SVG с явной нормализацией и строгой валидацией;
- стабильные ключи и codepoint, генерируемый типизированный manifest;
- детерминированный pipeline `SVG → TTF → WOFF2`;
- тонкий `Icon` с контрактом размера, цвета и accessibility;
- навыки `build-icon-font` и `update-icon-set`;
- поток обновления с классификацией и защитой от breaking changes.

Технология: icon font признан рабочим для монохромного fill-based набора.
Прямого сопоставления с inline SVG по единым критериям не проводилось, поэтому
вывод — «подходит для текущего сценария», а не «лучше».

Проверка пользователем: набор расширен до 17 glyphs добавлением иконок из
design-system панели через другую сессию агента; это подтверждает, что навык и
инструменты работают без контекста автора.

Урок процесса: путь был перегружен повторным обсуждением уже согласованных
решений и избыточными прогонами проверок; ledger заполнялся частично
ретроспективно. Подробная оценка целей и процесса — `notes/retrospective.md`.

Не вошло и продолжается отдельно:

- иконки из внешних паков;
- ассеты вне шрифта (возможно отдельный `Logo`);
- многоцветность и независимые от имён файлов публичные ключи;
- следующий цикл — `../../../outputs/shared/notes/landing-system-roadmap.md`.
