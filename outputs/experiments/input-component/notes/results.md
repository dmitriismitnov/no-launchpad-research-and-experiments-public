# Input Component — итоги эксперимента

**Статус:** эксперимент **закрыт** (2026-09-30) по прямой команде пользователя.
Ветка `experiment/input-component` не влита на момент закрытия (вливание —
отдельная команда). Ниже — итог билдера, вывод пользователя и направление
следующего цикла.

## Что не делалось намеренно

Границы scope, а не дефекты:

- `Textarea`/`multiline`, headless-интеграция (zagjs/Ark UI);
- size-варианты и responsive-размеры;
- `hint`-слот, счётчик символов, leading/trailing-иконки;
- `classNames`-per-slot escape-hatch (backlog `component-slot-classnames`);
- создание/изменение навыков.

## Что отложено

- Реальный mono-шрифт для лейбла: сейчас `body` + `xs` + `medium` + `wide` +
  `uppercase` — осознанная аппроксимация (font-pipeline вне scope).
- Системная проверка контраста placeholder/лейбла как cross-projection пар —
  точные пары Input проверены рецептом и browser-проверками, но правило не
  поднято в foundation.
- Computed-сравнение фокус-кольца Input и Button: рецепт-тест доказывает
  идентичность правил, программный фокус на кнопке не даёт `:focus-visible`.

## Что улучшилось по ходу

- Погружение через спецификацию выявило рассинхрон плана: Self-Review обещал
  покрытие `Review Focus` 1–6, а перечень тестов Task 2 покрывал 4 из 6. Два
  недостающих входа закрыты регрессиями (проверено негативным контролем).
- Инструментальная визуальная проверка вместо ручной: headless Chromium по
  `iframe.html` снял вычисленные стили и скриншоты, не требуя десктоп-браузера.
- Поведенческая (а не только структурная) проверка подтвердила, что нативная
  семантика `<input>` достаточна: focus-visible, disabled, invalid, связь ошибки
  работают без headless-слоя.

## Оценка автономности (билдер)

Автономность высокая для реализации и проверки: план был полным (точные пути,
токены, код, команды, ожидаемые результаты), поэтому работа шла почти
транскрипцией с обязательными TDD-циклами. Отклонения минимальны и все
зафиксированы в `execution-log.md` (нет remote → без `git pull`; сгенерированный
`styled-system` не коммитится; безрамочное выражение в тесте заменено на
константу; headless визуальная проверка).

Единственное содержательное вмешательство — закрытие разрыва между
`Self-Review` и перечнем тестов Task 2: план декларировал покрытие
`Review Focus` 1–6, но два входа не были покрыты, и это выяснилось только при
сверке спецификации с планом, а не из плана напрямую. Урок: «покрытие
обещано» должно раскрываться в конкретные тест-кейсы, иначе обещание остаётся
декларацией.

## Вывод пользователя

В целом доволен результатом: работа достаточно автономная, сказать особо нечего,
все выводы предыдущего эксперимента подтвердились. Ключевой акцент: когда
появится детальная связка **дизайн → спецификация → правила + скрипты + скиллы**
и добавится поведение и логика сторов, разработка пойдёт быстро, дёшево и
качественно.

## Как улучшить процесс

### Правила (кандидаты в постоянные)

1. **«Обещание покрытия» → конкретные тест-кейсы.** В плане каждая декларация
   покрытия (Self-Review / Review Focus) должна раскрываться в явные именованные
   тесты внутри перечня Task, а не оставаться утверждением. В этом эксперименте
   два входа `Review Focus` были обещаны, но не покрыты перечнем Task 2 — урок.
2. **Владение a11y-атрибутами.** Компонент владеет `aria-invalid`/
   `aria-describedby` (и подобными): потребительские значения изымаются на входе,
   компонент выставляет их по своему состоянию. Это был review-minor; закрепить
   как правило до следующего form-контрола.
3. **Явная типографика контрола.** Form-контрол задаёт `body`/`sm`/`regular`/
   `normal` явно, а не наследует UA-размер (~16px). Зафиксировать как правило.
4. **Дедупликация shared-хелперов.** `hasText` (Card + Input) и литералы
   focus-кольца (Button + Input) дублируются. Вынести в общий util/foundation,
   когда появится третий потребитель (правило из backlog `typography`:
   composite-слой при повторе в 3+).

### Скрипты (исполняемые проверки)

1. **Уникальность имён рецептов при сборке** — чтобы `Object.assign` не
   перезаписывал одноимённый рецепт молча (уже в `agent-work-model`, всё ещё
   актуально).
2. **Computed-сравнение фокус-кольца между компонентами** — сейчас идентичность
   доказана на уровне рецепта; runtime-сравнение `:focus-visible` не снималось
   (программный `focus()` не включает его).
3. **Cross-projection contrast как системное правило foundation** — placeholder
   (`common.500.background` на `common.50.background`) и muted-текст проверены
   локально (Input, Card), но не подняты в foundation как правило.

### Скиллы (в отдельных экспериментах, как и решено)

1. **Component build skill** — порядок declarations, публичное выше private.
2. **Component review skill** — API ownership, пустые области, prop-spreads/
   defaults, валидность CSS/Panda, границы inline HTML, локальность fixtures,
   testable geometry, актуальность docs.
3. **Code-smell checklist** — без размножения источников истины, без
   story-only экспортов, без комментариев без неочевидной причины.

### Связка дизайн → спецификация → правила

Главный вывод пользователя: mono-font аппроксимация и PEN→token снэпы
(46→50px, 14→12px, 7→6px) сейчас — ручные решения. Их систематизация — задача
трека `pen-design-system-integration` (связь PEN-переменных с PandaCSS-токенами),
а не отдельного компонентного эксперимента.
