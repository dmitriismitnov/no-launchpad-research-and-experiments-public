# Landing System Roadmap

Общая заметка вне эксперимента. Направление следующего цикла после закрытия
`semantic-color-foundation`.

## Конечная цель серии

Правила и workflow для реализации лендингов через дизайн-систему. Побочный
результат — шаблон лендинга.

Два столпа:

1. **Компоненты — основа.** Каждый компонент хорошо описан и документирован:
   что делает, как и по каким правилам.
2. **Системные правила**, которые мягко связывают компоненты между собой.

Идеальное решение: ядро с лучшими решениями для связи компонентов и
протоколами + отдельные компоненты и, возможно, плагины, помогающие именно в
реализации.

## Урок процесса

Высокоуровневую систему легко представить, но при реализации появляется так
много нюансов и деталей, что основная цель теряется.

- Сначала brainstorm: понять, что вообще нужно (сейчас это происходит
  неосознанно).
- Постепенно формировать видение, фиксировать результаты и планы миграций.
- После brainstorm — более направленный процесс.
- При сложностях и явных ошибках — снова brainstorm.
- Удерживать сложность и хорошие решения всего процесса, иначе постоянное
  буксование.

## Следующий цикл

Перед общим ревью всех пройденных этапов решить:

1. ~~Как работать с иконками.~~ Базовая модель сделана:
   [icon-asset-component](../../experiments/icon-asset-component/README.md)
   (монохромные иконки через icon font, навыки сборки и обновления). Осталось
   отдельно: иконки из внешних паков; ассеты вне шрифта (возможно отдельный
   `Logo`) — другой контракт изображения, а не только другой тип файла.
2. ~~Как работать с типографикой.~~ Базовая модель сделана:
   [typography-asset-foundation](../../experiments/typography-asset-foundation/README.md)
   (детерминированный pipeline `variable TTF → WOFF2 + manifest + generated CSS`,
   навык `build-web-font`, атомарные typography-шкалы и первая композиция
   `Button.label`). Осталось отдельно: subsetting, preload, composite text
   styles, responsive-шкалы, деструктивное обновление шрифта — детали в
   [backlog](backlog.md).
3. Зафиксировать, что все компоненты — включая саму страницу (её `background`
   — тоже background) — не выбиваются из общей шкалы.
4. ~~Сделать Input.~~ Первый поведенческий компонент `Input` закрыт —
   [input-component](../../experiments/input-component/README.md) (нативный
   `<input>`, `label`/`invalid`/`error`, focus/disabled, a11y через `aria-*`;
   без headless-слоя). Осталось отдельно: «сложное поведение» через zagjs/
   headless, `Textarea`, size-варианты.
5. ~~Сделать составной компонент.~~ Первый составной компонент `Card` закрыт —
   [card-component](../../experiments/card-component/README.md) (универсальный
   API, медиа с inline-заглушкой, действие футера, preset + stories + тесты).
   Модель и границы проверены в
   [итогах](../../experiments/card-component/notes/results.md).
6. Составить список компонентов, необходимых целевому лендингу, и реализовать
   их.
7. Провести ревью всех решений: где так, где не так.

Уточнение порядка (итоги `card-component`): ревью повторяющихся решений по
цветам и типографике, кристаллизация структуры кода/skills/scripts, настройка
ролей моделей и Storybook policy → остальные компоненты. Базовый `Input` закрыт
первым как проверка автономности (п.4), «сложное поведение» — отдельно.

Уточнение по ассетам (эксперимент `card-media-skeleton`, 2026-09-30): попытка
сделать SVG-картинку без pipeline закрыта как случайная. Вопрос «другой контракт
изображения» остаётся открытым — агент может выдать самодостаточный SVG-файл,
но нужен ли изображениям собственный pipeline, не исследовалось. Два пункта из
этого списка закрыты в `card-component`: подключение через `?raw` + inline с
наследованием `currentColor` работает, и ассет ведёт себя корректно внутри
реального `Card` в обеих темах.

Затем — ревью всех пройденных этапов серии экспериментов и фиксация
результата.
