# Agent Work Model

Общая заметка вне эксперимента. Две темы: модель работы с агентами через
эксперименты (skills, серии, трекер, процесс) и отдельный запрос — инструмент для
удобного просмотра истории git в терминале.

Материал — направление и backlog, а не план и не обязательство. При появлении
конкретной задачи тема может стать отдельным экспериментом.

## Часть 1. Модель работы с агентами

### Что подтверждается

- Работать с агентами по модели экспериментов нравится всё больше.
- Главное — очерчивать границы и не выходить за них.
- Маленькие очерченные эксперименты подходят для агентов лучше больших.
- Ценность накапливается не только в коде: каждый эксперимент подтверждает или
  уточняет саму модель работы (подробнее — ретроспектива
  `button-icon-composition`).
- Небольшой компонент агент способен собрать самостоятельно при наличии близкого
  образца и накопленных правил; противоречия правил и завершение задачи пока
  требуют внешнего процесса (опыт `button-icon`, раздел ниже).

### Skills для агента

Нужен набор проектных skills, в идеале по образцу superpowers.

Важное дополнение: skills должны уметь подавать **короткий контекст внутрь
сессии** — загружать по требованию компактный, актуальный контекст вместо
раздувания системного промпта.

Что стоит закрепить в наборе:

- границы эксперимента и предохранитель от расползания scope: агент может
  обнаружить смежную проблему, исследовать её в объёме текущей цели и
  **предложить** дальнейшую работу, но включение этой работы в эксперимент
  требует явного решения пользователя;
- полномочия агента в эксперименте и порядок принятия решений;
- критерии проверки и обязательность подтверждения результата;
- порядок фиксации выводов и закрытия эксперимента;
- порядок предложения агентом своих экспериментов.

Основа частично описана в [llm-wiki-skills](llm-wiki-skills.md) — там backlog
проектных skills, но только для операций LLM Wiki. Эту идею нужно расширить на
весь процесс эксперимента, а не только на wiki.

### Серии экспериментов

- Серия — это несколько связных экспериментов с **общим выводом в конце**.
- Общий вывод серии — отдельный артефакт, а не сумма выводов отдельных
  экспериментов.
- Конечная цель серии и её состав частично описаны в
  [landing-system-roadmap](landing-system-roadmap.md).

### Трекер

Нужен простой трекер задач:

- добавлять задачи по ходу дела;
- органично формировать план экспериментов через агента;
- агент может предлагать свои эксперименты;
- часть задач агент может решать автономно.

### Процесс

- Перенести техники agile/scrum на эксперименты.
- Добавлять waterfall там, где это возможно и полезно (например, там, где нужна
  строгая последовательность этапов).

### Открытый вопрос

Пока не до конца понятно, как один большой процесс с несколькими TODO выполнять
через разные сессии. Нужен способ сохранять и передавать состояние между
сессиями, чтобы работа не терялась и не дублировалась.

### Опыт `button-icon`

Эксперимент `button-icon` — первый, где агент работал по сырому заданию без
готовой модели: реализовать компонент из существующих деталей. Что показал:

- Агент самостоятельно нашёл контекст и собрал работающий компонент по одному
  образцу (`Button`) и накопленным правилам.
- Главный сбой: встретив противоречие правилу (объединение пресетов Panda), агент
  применил локальный обходной путь (`theme.extend`) и сообщил о потребности в
  решении только в отчёте. Действующее правило было изменено до согласования.
- Второй прогон, уже по направленному плану, прошёл чисто: агент убрал обходной
  путь, ввёл явную сборку словарей и регрессионный тест.
- Завершение (коммиты, повторные проверки, закрытие, вливание ветки) обеспечивал
  оркестратор.

Вывод: агент способен самостоятельно довести небольшой компонент до рабочего
состояния при наличии близкого образца, но работа с противоречиями правил и
завершение задачи пока требуют внешнего процесса. Результат честнее называть
«самостоятельная первая реализация с последующей архитектурной коррекцией», а не
полностью автономной разработкой.

Ограничение чистоты: отдельный список критериев наблюдения билдеру не
передавался, но критерии компонента были ему доступны в `README` эксперимента,
хотя он должен был работать по сырому заданию.

### Опыт `typography-asset-foundation`

Эксперимент по типографике прошёл автономно до конца: агент собрал asset-модуль,
pipeline, задачи, навык, foundation-токены и первую композицию компонента.

- Что сделало это возможным: очерченные границы scope, проектный skill
  (`build-web-font`) как операторский workflow, исполняемые задачи
  `fonts:build`/`fonts:check` и детерминированный pipeline с проверкой дрейфа.
- Проверки работают как исполняемые правила: семья, стиль, оси, диапазон
  `100–900`, magic header WOFF2 и drift артефактов падают, а не предупреждают.
- Автономность не отменила ревью: независимый разбор нашёл реальные пробелы
  (generated CSS не был контрактом, источник валидировался дважды), после чего
  pipeline усилили.
- Урок, повторённый пользователем: правила, skills и scripts — основной рычаг
  разработки агентами, важнее объёма кода в отдельной сессии.

### Опыт `card-media-skeleton`

Короткая проба: может ли агент сгенерировать SVG-картинку. Ответ — да. Ценность
дал не результат, а ошибка процесса.

- Пользователь просил ассет; агент развернул это в эксперимент о контракте
  изображений и в roadmap-пункт «ассеты вне шрифта».
- Рамка оказалась шире замысла: вопрос, записанный в `README`, пользователь не
  задавал, и он остался нерешённым. Пользователь закрыл эксперимент как
  случайный.
- Вывод: различать **пробу способности** («может ли модель сделать X», ответ —
  да/нет, артефакт можно выбрасывать) и **дизайн-эксперимент** («как это должно
  быть устроено», нужны scope и критерии). Для пробы достаточно короткого
  вопроса, а не `README` с моделью и критериями.
- Вывод: не поднимать статус задачи до эксперимента без запроса — «сделай X» не
  означает «исследуй, как устроить X».

### Что улучшить для автономной работы

- **Полномочия при противоречии правилам.** Различать случаи: нет подробности
  (локальное допущение с обоснованием), противоречие правилу (воспроизвести,
  предложить варианты и спросить до закрепления обхода), нужна смежная работа
  (обосновать расширение рамок).
- **Исполняемые правила.** Правило, подкреплённое проверкой, надёжнее повторного
  чтения заметки. Ценный побочный результат эксперимента — регрессионный тест
  сборки пресетов; следующий шаг — проверять уникальность имён при сборке, чтобы
  `Object.assign` не перезаписывал одноимённый рецепт молча.
- **Однозначные условия завершения.** В задании явно фиксировать обязательные
  проверки, обращение с visual baseline, нужны ли коммиты, состав отчёта и
  границы ответственности оркестратора и пользователя.
- **Проверять поведение, а не только структуру.** Для `ButtonIcon` полезнее
  сценарии Enter/Space, отсутствие активации при `disabled`, доступное имя, фокус
  и сохранность рецептов в итоговой конфигурации.
- **Актуальность контекста.** Явно размечать текущее правило, исторический вариант
  и замену, чтобы агент не догадывался.
- **Скрипты вместо повторений.** Кандидаты: фиксация состояния эксперимента, набор
  проверок, сводка изменений, проверка условий передачи результата, обновление
  статусов — см. [script-first-flows-and-agent-workspace](script-first-flows-and-agent-workspace.md).
- **Чистота теста автономности.** Фиксировать доступные билдеру материалы, держать
  критерии наблюдателя вне его рабочего контекста и различать самостоятельный
  прогон и направленные доработки.

## Часть 2. Просмотр истории git для ревью

Отдельный запрос, не относится напрямую к разработке.

Нужен инструмент для удобного просмотра истории git при ревью.

- Сейчас используется VS Code — неудобно.
- Цель — полностью переехать в терминал.
- Два варианта:
  1. разобраться, как это делать в Neovim;
  2. найти отдельный инструмент.

Уточнение по названиям: упомянутый «AstroVim» был переименован в **LazyVim**;
**AstroNvim** — отдельный проект. Стоит уточнить, о каком именно дистрибутиве
речь, прежде чем выбирать (не проверялось в этой сессии).

Кандидаты к рассмотрению (не проверялись в этой сессии):

- отдельные TUI: `lazygit`, `tig`, `gitui`;
- внутри Neovim: `fugitive`, `neogit`, `diffview.nvim`.

Что важно для сценария ревью: просмотр истории ветки, диффы по коммитам, работа
с индексами и hunks, удобный blame. Конкретный выбор — отдельная задача.
