# Многоагентная оркестрация в OpenCode

## Цель

Настроить устойчивый конвейер для инженерных задач, в котором разные роли
выполняются разными моделями и могут продолжать работу после compaction
контекста:

```text
orchestrator (модель A)
  → planner (модель B)
  → builder (модель C)
  → reviewer / verifier (модель D, при необходимости)
```

Оркестратор последовательно запускает роли, принимает их результаты и
передаёт следующей роли только проверенные и сохранённые артефакты.

## Возможности OpenCode

OpenCode поддерживает custom agents с отдельными system prompt, моделью,
режимом работы и permissions. У субагента `model` задаётся независимо; если
она не задана, он наследует модель родительской сессии.

Субагенты запускаются в дочерних сессиях с чистым контекстом. Родитель видит
итоговый результат как результат tool call, но не получает автоматически
полную внутреннюю историю субагента. Поэтому результат роли должен быть
структурированным и передаваться дальше явно.

Встроенный `general` предназначен для многошаговой работы, но не может
запускать других субагентов. Для этой схемы нужен отдельный `orchestrator` с
разрешением `subagent` на конкретные роли.

Источники:

- [OpenCode — Agents](https://opencode.ai/v2/docs/agents/)
- [OpenCode — Configuration](https://opencode.ai/v2/docs/config/)

## Роли и границы ответственности

### Orchestrator

**Модель:** A, выбранная для основной сессии или как default model проекта.

**Ответственность:** управлять переходами между ролями; не выполнять
реализацию самостоятельно.

Обязательный порядок:

1. передать задачу planner;
2. получить и сохранить план;
3. передать builder путь к плану и его версию;
4. передать reviewer план, журнал выполнения, diff и результаты проверок;
5. закрыть задачу только после проверки.

### Planner

**Модель:** B.

**Права:** read-only, без редактирования и shell-команд, которые меняют
проект.

**Результат:** структурированный план с критериями готовности, затрагиваемыми
файлами, порядком шагов, рисками и командами проверки.

### Builder

**Модель:** C.

**Права:** только те, что нужны для реализации и верификации.

**Результат:** реализация, обновлённый execution journal, результаты проверок
и точный следующий шаг либо описание блокера.

### Reviewer / verifier

**Модель:** D.

**Права:** обычно read-only; отдельное изменение возможно только при явно
выбранном remediation этапе.

**Результат:** findings с уровнем критичности, проверка критериев готовности и
вердикт `verified`, `changes-requested` или `blocked`.

## Контекст и compaction

Compaction заменяет старую историю сессии summary, оставляя system prompt и
последнюю часть диалога. По умолчанию сохраняется около 15 000 последних
токенов. Summary является lossy: ранние сообщения и детали tool output могут
исчезнуть.

При compaction актуальные instruction files снова применяются как baseline.
Поэтому постоянные правила не следует хранить только в сообщениях чата.

Источники:

- [OpenCode — Compaction](https://opencode.ai/v2/docs/compaction/)
- [OpenCode — Instructions](https://opencode.ai/v2/docs/instructions/)

### Непотеряемые правила

Короткие инварианты роли должны находиться в system prompt агента:

- orchestrator всегда соблюдает `planner → builder → reviewer`;
- orchestrator не редактирует проект сам;
- builder работает только по утверждённому плану;
- builder перед действием восстанавливает статус из durable state;
- reviewer не объявляет работу завершённой без проверяемых доказательств.

Не нужно дублировать в system prompt весь подробный workflow: это увеличивает
фиксированный контекст каждой модели и создаёт риск рассинхронизации.

### Конфигурация compaction

Увеличенный хвост недавней истории снижает риск потери свежих деталей, но не
заменяет durable state:

```jsonc
{
  "compaction": {
    "auto": true,
    "keep": { "tokens": 24000 },
    "buffer": 16000
  }
}
```

В V2 нет настройки, которая заставляет compaction summary всегда включать
произвольный набор пользовательских правил. Инварианты нужно хранить в system
prompt/instruction files, а изменяемое состояние — в файлах задачи.

## Skills

Skills не являются постоянным полным prompt. На каждом шаге модели доступен
только каталог skills — ID, имя и description. Полное содержимое `SKILL.md`
добавляется в разговор только после вызова инструмента `skill` или явного
упоминания `@skill-id`.

Следствие: после compaction список skills остаётся доступен, но ранее
загруженное тело skill может быть сжато. Role skill нужно загружать в
естественных точках процесса: перед стартом задачи, перед сменой этапа и при
возобновлении после блокера.

Рекомендуемая глобальная структура:

```text
~/.config/opencode/skills/
├── orchestrator-protocol/SKILL.md
├── planner-protocol/SKILL.md
├── builder-protocol/SKILL.md
└── reviewer-protocol/SKILL.md
```

System prompt роли должен требовать загрузить свой protocol skill перед
началом нового этапа. Permissions агента следует ограничить только
необходимыми skills; в правилах permissions последнее совпавшее правило имеет
приоритет.

Источник: [OpenCode — Skills](https://opencode.ai/v2/docs/skills/).

## Durable state и передача между агентами

Skills описывают процедуру, но не хранят рабочее состояние задачи. Source of
truth для выполнения — файлы задачи, а не chat history и не краткое
пересказывание оркестратора.

Минимальный набор артефактов:

```text
<task>/
├── plan.md
├── execution-journal.md
└── review.md
```

### plan.md

Создаётся planner и содержит:

- цель и критерии готовности;
- границы задачи и допущения;
- атомарные шаги;
- файлы и зависимости;
- риски;
- команды и критерии проверки;
- версию или идентификатор плана.

### execution-journal.md

Создаётся и поддерживается builder. После каждого логического этапа он
фиксирует:

```md
## Current state

- Completed: …
- Changed files: …
- Verification: команда → результат
- Decisions: …
- Blockers: …
- Next action: один точный следующий шаг
```

Перед возобновлением builder обязан:

1. прочитать plan.md и execution-journal.md;
2. сверить заявленное состояние с `git status`, `git diff`, файлами и
   доступными результатами тестов;
3. продолжать только с `Next action` либо зафиксировать расхождение как
   blocker.

### review.md

Создаётся reviewer и содержит результаты проверки, связанные с критериями
готовности, evidence и итоговый статус.

Передача между ролями должна состоять из путей к этим файлам, идентификатора
или версии плана и краткой инструкции роли. Не следует передавать только
пересказ чата: он не является надёжным после compaction и в свежей дочерней
сессии.

## Дисциплина выполнения

Для длинных задач builder обязан разбивать работу на небольшие атомарные
этапы. Каждый этап завершается только после записи фактического результата в
journal. Запись должна происходить не только в конце всей задачи: иначе
compaction, сбой или смена сессии оставят изменения без объяснения.

Явные статусы процесса:

```text
planned → implementing → ready-for-review → verified → done
                         └→ blocked
```

Оркестратор не переводит задачу дальше без необходимого артефакта и evidence:

- `planner → builder`: plan.md утверждён и имеет критерии готовности;
- `builder → reviewer`: journal содержит изменения и результаты проверок;
- `reviewer → done`: review.md подтверждает критерии либо описывает
  `changes-requested` / `blocked`.

## Paperclip: когда нужен

Paperclip может быть внешним control plane поверх OpenCode: он предлагает
оргструктуру, задачи с ответственными и зависимостями, approval gates,
heartbeats, бюджеты и долговременный audit trail. Это оправдано для
долгоживущей многопроектной команды агентов, расписаний, параллельных
направлений и жёсткого контроля расходов.

Для одного интерактивного инженерного конвейера Paperclip избыточен: OpenCode
agents, role skills и durable task artifacts покрывают основную схему с
меньшей операционной сложностью.

Если Paperclip подключается позднее, он должен быть внешним уровнем
управления задачами, а OpenCode — инженерным runtime. Нельзя одновременно
делать и Paperclip, и OpenCode независимыми главными оркестраторами.

Источник: [Paperclip — Bring Your Own Agent](https://paperclip.ing/product/bring-your-own-agent/), [Paperclip — Tasks](https://paperclip.ing/product/tasks/).

## Итоговая модель

```text
System prompt роли
  = короткие неизменные инварианты, переживают compaction

Role skill
  = подробный повторяемый workflow, загружается перед этапом

Task artifacts
  = plan.md + execution-journal.md + review.md,
    единственный источник истины о текущей работе

OpenCode orchestrator
  = последовательные переходы ролей и handoff по файлам
```

Эта модель превращает compaction из риска потери рабочего состояния в обычное
возобновление: агент применяет постоянные правила роли, загружает workflow,
читает durable state, сверяет его с репозиторием и продолжает с точного
следующего шага.
